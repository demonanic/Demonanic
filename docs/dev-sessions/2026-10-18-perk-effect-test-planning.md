# Perk Effects: Documentation and Test Plan

## Scope

Read the Phase 0 roadmap and report, rechecked current perk catalog, source consumers, and frontend tests. The latest read-only audit is available in the conversation history; its findings were treated as hypotheses and checked against the current source. This is a planning-only pass. No gameplay, balance, profile, or test files were changed.

Current branch is `feature/castle-management-first-pass`, HEAD `7fb3d67 Fix tower placement position consistency`. The existing dirty worktree was preserved.

The descriptions below are the only documented intent found in the catalog. Where they do not define mechanics (targets, thresholds, duration, stacking, source/recipient, or damage path), this plan does not assume a design choice.

## Existing test coverage and gaps

- `engine.defense-perks.test.js`: tests Defense baseline vs stat/gear/Bulwark inputs through direct, projectile, and area hits; finite values across current perk catalogs; Escape Artist threshold and combat dodge. It does not test all other effects, malformed effect definitions, save/load, or effect-specific scaling for non-Defense perks.
- `engine.abilities.test.js`: tests starter ability availability/effects, cooldowns, invalid targets, and Mage Mend at default values. It does not prove passive perk modifiers.
- `engine.targeting.test.js`: tests targeting/range/cooldown interactions and Mage spell action lifecycle. It does not test perk-granted range or damage modifiers.
- `logic.progression.test.js`: tests pending AP/SP draft and confirmation behavior, not combat effect consumers or profile round-trip.
- Current frontend suite has no direct regression tests for the remaining effect multipliers, reactive support distinction, AoE flag consumption, burn, Lifebloom, marks, Ghoststep, Fortress reduction, Last Stand Defense, Guardian reaction duration, or Cleave.

## Minimal implementation and test order

1. **Effect contract tests, no behavior change:** add table-driven checks that every catalog effect key has a typed/defaulted handler or an explicitly classified metadata status. Include wrong-type, negative, `NaN`, and infinite catalog values. Decide whether negative effect values are rejected or supported.
2. **Existing, deterministic stat effects:** test exact derived `maxHpPct`, `attackRatePct`, `range`, `moveSpeedPct`, `critChancePct`, `dodgePct`, `healPct`, `barrierPct`, and cooldown scaling against current formulas. Implement only where the tests expose a mismatch and intended scope is explicit.
3. **Resolve cross-path modifiers before coding:** approve scope for `abilityDamagePct`, `lowHpDamagePct`, `highHpDamagePct`, `critHealPct`, `cooldownPct`, and `multiTarget`; add attack/ability/spell matrix tests before changing consumers.
4. **Implement target/status effects only after decisions:** choose exact mechanics for `cleave`, `damageReductionPct`, `lowHpDefense`, `reactionBonus`, `reactiveSpeedPct`, `burn`, `lifebloom`, `markedDamagePct`, and `reactiveSupport`. For `aoe`, decide whether to remove/retain it as redundant metadata or make it authoritative for unlock behavior.
5. **Persistence/compatibility gate:** once a behavior slice is approved, verify legacy perk IDs and purchased perks survive normalize/save/load unchanged; runtime statuses remain battle-only; repeat normalization is idempotent.

### Decisions requiring approval

- Whether “ability” includes Mage spells and ordinary attacks for damage/cooldown/multi-target modifiers.
- Whether ability-specific perks apply only to matching abilities, and how Rogue Combo’s “successive strikes” are tracked.
- Archer Execution’s threshold (description says 25%; handler uses 35%) and whether low/high-HP perks affect basic attacks.
- Barrier scaling ownership (caster or recipient) and whether Arcane Ward and automatic support barriers are included.
- Cleave and MultiShot target selection, secondary damage, target count, range, and recursion behavior.
- Defense reduction/conditional Defense order with the existing Defense formula and shields.
- Reaction duration units/trigger scope, and whether reactive support is already baseline behavior or should be perk-gated.
- Burn/mark/shield status duration, stacking, refresh, attribution, death cleanup, and immunity.
- Whether `aoe` is redundant metadata or should drive Firestorm availability/behavior.

Until these decisions are recorded, the safe next work is test-only characterization of explicitly specified current formulas, followed by approval for any consumer behavior changes. Do not advance to Phase 1 or change gameplay in this planning pass.
