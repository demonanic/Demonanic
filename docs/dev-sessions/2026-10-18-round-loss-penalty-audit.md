# Round-Loss Penalty Audit

**Scope:** Read-only audit of defeat handling, state persistence, retry/recovery options, and documented intent on `feature/castle-management-first-pass`. No gameplay code was changed.

## Executive summary

Losing a round has meaningful, mostly persistent consequences, but not a single automatic defeat fee. The battle result saves combat damage, resource use, morale changes, casualties, and destroyed towers; the wave does not advance, and the player can retry that same wave after choosing a recovery route. Kills made before defeat still grant Gold, XP, kill counts, and possible Vault equipment drops.

Two material discrepancies stand out. The advertised surrender Gold tax is recorded and displayed but never deducted. Also, the Results-screen mock-ad revive restores the squad, towers, and castle even if its reward request fails; the current backend mock always grants the request, but the client failure path is fail-open. Repeated failed attempts can also retain kill rewards and repeat the same wave, making partial-kill reward farming possible.

## Defeat, recovery, and retry paths

- Defeat is triggered when all heroes are down, castle HP reaches zero, or a strict majority of enemies breach. Victory is a separate engine condition (`frontend/src/game/engine.js:1717-1777`).
- `Battle.onEnd` rechecks defeat conditions before presenting Results, saves runtime combat state on both outcomes, and only calls `completeWave` when the result is still a victory (`frontend/src/screens/Battle.jsx:85-155`). I found no normal loss path that also grants wave-completion progression.
- Results offers one-time Free Life, mock-ad revive, or Surrender. Free Life reduces Gold/Stone/Metal to 30%, restores heroes, towers, and castle, and resets morale to 20. Mock-ad revive restores heroes, towers, and castle without the Free Life resource reduction; it does not reset morale or restore tower ammunition/mana. Surrender applies the morale penalty and returns Home without advancing the wave. From there the same wave remains available after preparation.
- The mock reward endpoint is intentionally unconditional today (`backend/server.py:188-200`; `backend/tests/backend_test.py` tests that mock grant). Separately, `Results.doRevive` catches a reward-request error and proceeds with restoration anyway (`frontend/src/screens/Results.jsx:19-25`). Thus a rejected/failed request would still grant the in-game revive. Preparation's individual ad-revive path checks `data.granted`; Results does not.
- `GameProvider.mutate` immediately writes a local backup and schedules a debounced backend save if enabled. The battle result itself is not saved as a live simulation snapshot: if the app is closed before `onEnd`, only the provider state (plus its normal research ticks) is saved, not the battle engine's accumulated combat changes. This means abandoning/restarting mid-wave can replay from the pre-result saved combat state. This is inferred from the runtime ownership/save path, not covered by a test.

## Documented intent versus implementation

| Documented intent | Implementation comparison |
|---|---|
| `plan/plan.md:23,33,49` describes a one-time Free Life retaining progression but only 30% resources, additional mocked revival, and surrender with penalties and a Gold tax. `memory/PRD.md:50` likewise specifies surrender Gold tax plus morale. | Free Life's resource reduction and restoration are implemented. Surrender's morale penalty is implemented, but its Gold tax is not: `surrender()` only sets `surrenderTaxRate` / `surrenderDebtWave` and applies morale (`logic.js:901-904`). Those markers are only read by the Home banner and cleared on victory (`Home.jsx:110-113`, `logic.js:912-914`); no rate is applied to Gold production or earnings. The Results message therefore claims a tax that is not charged. |
| The documented flow returns players from Results to Preparation and frames losses as recovery choices. | The wave index is retained after defeat; a player can retry it after a recovery option. The design docs do not state whether kill rewards should persist across failed attempts or whether mid-wave app exit should roll back an attempt. |
| `plan/plan.md` describes buildings, towers, barricades, and resource production as core systems. | Tower and building combat damage persists, but barricade combat damage is lost because `Battle.onEnd` omits barricades. Building damage can reduce future production. No explicit building repair helper/UI was found in the inspected frontend paths; whether another recovery route is intended should be confirmed before treating destroyed buildings as permanent. |

The design references also differ from the current state schema: they mention Food, while current `createNewState` stores Metal in its place (`frontend/src/game/logic.js:125-133`). This audit treats the code as authoritative for actual behavior and does not infer a Food loss penalty.

## Findings and follow-up plan

1. **High — make Results revive fail closed.** Require a successful, explicitly granted reward before restoring the squad/towers/castle; surface a failure without granting the revive. Add tests for rejected requests and `{granted:false}`.
2. **High — define and enforce retry reward policy.** Failed attempts currently retain kill rewards and can be repeated on the same wave. Decide whether per-kill rewards are intended to be repeatable, then add loss/retry tests for Gold, XP, drops, and kill totals. Consider separately documenting the mid-wave app-exit behavior.
3. **Medium — implement or remove the surrender-tax claim.** The current UI displays a tax and Results says it is applied, but no deduction exists. Follow the authoritative balance design before implementing any deduction; alternatively remove the claim/marker if no tax is intended.
4. **Medium — decide barricade persistence.** Determine whether damage should persist across results. If yes, copy validated barricade HP into saved state and test defeat and victory paths; if no, document the reset behavior.
5. **Medium — add battle-result regression coverage.** Cover loss reasons, state persistence, no victory progression on defeat, recovery choices, and no duplicate `onEnd` reward processing.

## Verification limits

This was a source-and-documentation audit; no gameplay code was changed and no tests were run. No test covering the full defeat → persistence → recovery/retry flow was found. The mock reward endpoint has a backend test proving that its current authenticated mock always grants; that test does not prove the Results client handles denial or failure correctly. All claims above are therefore based on inspected implementation unless explicitly marked as test coverage.
