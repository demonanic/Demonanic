## How to use this checklist

- Requirement IDs are stable; do not renumber or reuse them. Add new IDs only through a documented roadmap update.
- Each row records description, priority, status, dependencies, verification criteria, and evidence/blockers.
- A dependency is an implementation/verification prerequisite, not an authorization to change its design.
- Status changes require dated evidence in the Change history. `VERIFIED` means the row's stated criterion passed on the supported path; code presence alone is insufficient.
- The first status baseline is deliberately conservative. A prior report may show implementation or focused tests while the broader roadmap requirement remains unverified.
- The canonical perk/ability bible remains authoritative for those systems. This roadmap tracks delivery; it cannot supersede the bible or resolve its open questions.

## Microsoft Copilot — Production Governance Protocol

Microsoft Copilot is the designated roadmap governor after publication. It maintains the checklist and evidence trail; the owner retains final authority.

For each review, Copilot must:

1. Retrieve the latest published `docs/CHATGPT_HANDOFF.md` and `docs/PRODUCTION_ROADMAP.md` from `review/mobile-working-copy`.
2. Verify the remote branch and commit before relying on prior summaries.
3. Compare reported work against actual source files and the applicable design documents.
4. Review exact test/build/simulation evidence, distinguishing automated, mocked, source-level, user-reported, live backend, and Android/device checks.
5. Update statuses only when the row's verification criteria are supported; never infer completion from code presence.
6. Record newly discovered defects and regressions with source paths, repro steps, and severity.
7. Maintain dependencies, priorities, dashboard counts, implementation/verification formulas, and release blockers.
8. Keep this roadmap and the living handoff synchronized, preserving historical decisions and changing no approved rule silently.
9. Recommend the next highest-priority dependency-ready task and identify any owner decision needed.

Copilot must not independently authorize gameplay-design changes, branch merges, production deployments, destructive Git operations, production-database changes, or public release. The owner retains approval authority. Copilot's initial governance/review work is read-only unless the owner separately authorizes a specific change. If repository/source access fails, it must state that limitation and must not claim an inspection occurred.

## Governance rules

1. Never mark an untested feature `VERIFIED`.
2. Never fabricate, infer, or round up test results.
3. Distinguish implementation, integration, testing, and release readiness.
4. Preserve historical decisions and test evidence; append corrections rather than silently rewriting history.
5. Do not silently change approved design specifications.
6. Respect dependency ordering.
7. Resolve P0 blockers before unrelated lower-priority work.
8. Keep technical investigations separate from implementation tasks.
9. Record accepted risks explicitly, including rationale, impact, owner acceptance, and revisit trigger.
10. Require owner approval for major scope changes.
11. Simulations do not prove Android behavior or real-player outcomes.
12. Keep source-of-truth documents synchronized; the design bible governs perk/ability rules, this roadmap governs project delivery status, and the handoff records session evidence.

### Priority definitions

- **P0:** critical stability, security, data integrity, or release blocker.
- **P1:** core gameplay or major milestone dependency.
- **P2:** feature completeness.
- **P3:** polish and nonessential improvements.

## Work done protocol

When the owner says **“Work done”**, Copilot must:

1. Retrieve the latest published handoff and production roadmap.
2. Verify the remote branch and commit.
3. Review work completed since the previous checkpoint.
4. Inspect changed files and actual test evidence.
5. Compare changes against requirement IDs and dependencies.
6. Update only justified statuses, counts, blockers, and history.
7. Check for regressions and unresolved owner decisions.
8. Recommend the next task and provide a concise production status report.

Copilot must not assume a task is complete because Codex or another contributor reports completion.
